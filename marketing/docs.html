Part 1 · Get started

1. Quick start

  1. Flash the appliance image to USB, or PXE-boot it.
  2. Enter a 5-digit Chain of Custody ID (COCID) when prompted.
  3. tScrub discovers every drive and maps it to its strongest wipe capability.
  4. Watch live progress; each drive ends with a status (COMPLETED, FROZEN, BLOCKED, or FAILED).
  5. Collect the report files, which are written to the report directory.

2. System requirements

  • x86-64 machine with USB or PXE boot
  • Linux kernel with root access
  • 1 GB RAM (erasure runs in parallel)
  • Dependencies: nvme-cli, hdparm, nwipe (SCSI), lftp (optional upload), openssl (signing)
  • Drives must not be in use by the host OS

Part 2 · Build & run

3. Build your appliance

tScrub is a single self-contained script. Build it from source, then boot it on any Linux environment with the dependencies above.

make build
# produces build/tscrub.sh
  • Place the sedutil-cli binary in payload/ before building (it is embedded as base64).
  • For a Team/Enterprise build, place the vendor public key at payload/vendor-public-key.pem so tScrub can verify licences.
  • Boot with root access; the script detects and sanitises NVMe, SATA, and SCSI drives.

4. Run a sanitisation job

tscrub                      # full run (wipes all supported drives)
tscrub --dry-run            # discover and classify, wipe nothing
tscrub --dry-run --simulate-running-eta=10   # simulated run with live progress

tScrub prompts for a COCID, then wipes all supported drives in parallel. Frozen, locked, or blocked drives are flagged rather than marked clean.

Part 3 · Reports

5. The report

Each job produces three files:

tscrub_48213_20260912T1030Z.csv    # human-readable report (one row per drive)
tscrub_48213_20260912T1030Z.sig    # base64 Ed25519 signature over the CSV
tscrub_48213_20260912T1030Z.json   # manifest (SHA-256, public key, drive summary)

The CSV columns are: COCID, Timestamp, Model, Serial, Size, Bus, Type, Device, Class, Certification, Method, FinalStatus.

Uploading reports

tScrub can upload all three files to an FTP server at the end of a run. The destination is set at boot time on the kernel command line (PXE, GRUB, or the ShredOS boot entry) — not inside the script:

shredos_output=ftp:host:path:user:password
# e.g. shredos_output=ftp:backup.example.com:incoming/tscrub:itad:s3cret

ftp is the protocol (FTP only). host is the FTP server, path is the remote directory (relative to the FTP user's home, no leading slash), then the username and password.

The password must not contain spaces or colons, and credentials are visible in the boot configuration — use a dedicated FTP account.

6. Verify a report

Anyone can verify that a report is unchanged and, where licensed, attributable:

tscrub verify tscrub_48213_20260912T1030Z.csv
# SHA-256: 4614d837...
# Manifest: OK
# Signature: VALID

You can pass a public key explicitly: tscrub verify report.csv public-key.pem. A tampered report fails with MISMATCH or INVALID.

7. Certificate of Destruction

Turn one or more tScrub reports into a single, printable Certificate of Destruction at tscrub.com/certify. Upload the .csv (and, if you have them, the matching .json and .csv.sig) files — reports sharing the same Chain of Custody ID are consolidated into one certificate.

What happens when you upload

  1. Each .csv is hashed (SHA-256) and, when a manifest is present, checked against its recorded checksum.
  2. Where a report is signed, the Ed25519 signature is verified against the key embedded in the manifest.
  3. Drives from every report with the same COCID are merged into a single certificate, sorted by wipe time.
  4. A tamper-evident PDF is generated with a unique Certificate ID, an annex listing every device, and a verification QR code.

Verifying a certificate online

Each certificate carries a unique Certificate ID (COD-…). Scanning the QR code — or visiting tscrub.com/verify?cert=COD-… — looks up the issuance record and confirms:

  • the Certificate ID, Chain of Custody ID, and sanitisation window;
  • device, method, and run counts;
  • the integrity and signature status recorded at issuance;
  • a SHA-256 hash of the PDF itself, so the document can be checked for alteration since issue.

Part 4 · Reference

8. Licensing

TierReport signing
Without a licenceSelf-signed (proves integrity, not identity)
Team / EnterpriseVendor-issued key (proves attribution to a customer)

A license.key contains a signed report-signing key. At boot, tScrub verifies the licence signature and expiry, then signs reports with the licensed key.

# Vendor side: issue a licence
scripts/issue_license.sh "Acme ITAD Ltd" 2027-09-12 vendor.key license.key

Attaching a licence

The appliance reads the licence from /etc/tscrub/license.key by default. When running the script directly, either place the issued .lic file there or point to it with --license:

mkdir -p /etc/tscrub && cp "Acme-ITAD-Ltd-2027-09-12.lic" /etc/tscrub/license.key
tscrub --license /path/to/Acme-ITAD-Ltd-2027-09-12.lic

For ShredOS / PXE boots, set the licence path on the kernel command line. tScrub checks both parameter names (same style as the FTP upload destination):

tscrub_license=/etc/tscrub/license.key
# or: shredos_license=/mnt/usb/license.key

The licence can also be fetched over the local network instead of a filesystem path. Use --license-url when running directly, or the URL form of the kernel parameter for ShredOS/PXE boots:

tscrub --license-url http://192.168.1.10/license.key
tscrub_license_url=http://192.168.1.10/license.key
# or: shredos_license_url=http://192.168.1.10/license.key

Fetching requires curl or wget on the appliance. Because a .lic contains the private report-signing key, host it on an authenticated or isolated LAN endpoint — not a public URL.

Team/Enterprise appliances can ship with the licence baked in at build time, so nothing needs to be supplied at boot:

# Vendor side: build a customer image with the licence embedded
make build-customer CUSTOMER="Acme ITAD Ltd" LIC=/path/to/Acme-ITAD-Ltd-2027-09-12.lic

The embedded licence is still verified at boot (signature + expiry). An explicit --license, --license-url, or kernel-command-line value takes precedence over it.

A licence is only verified on Team/Enterprise builds that embed the vendor public key; the free community build ignores it and keeps self-signed reports.
