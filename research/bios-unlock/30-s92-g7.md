## 7. V2 RESULT — RE-INJECTION CONFIRMED (2026-11-17)

Flashed the V2 probe; password remained. Afterflash dump
(`W25Q256FV_SOIC8-CND14004KD-AFTERFLASH.BIN`, md5
`a1327983a9deed7e441425b99e7f1707`) shows:

- the patched entry @0x18D4A58 **stayed deleted** (0xFD) — the firmware did
  not resurrect it;
- a **NEW live UserCred @0x18E1DC4 (0x3F)** appeared with the ORIGINAL locked
  content — the EC mirror re-injected the credential as a new entry;
- a transitional entry @0x18DEF30 in state 0x3C (ADDING) with zeroed content —
  the staging artifact of that SetVariable.

So S92 01.08 restores the credential from the EC whenever no LIVE UserCred
exists — exactly the 830 G5 ≥01.24 behaviour.

## 8. V3 — empty LIVE UserCred (built, awaiting bench)

**Key insight:** on the 830 G5, units unlocked via KEEPBB kept an EMPTY live
UserCred (no AdminPW record) and stayed unlocked even after a BIOS update to
mirror-era code — i.e. mirror-era code validates against the STORE and does
NOT re-inject while a live UserCred exists. The EC mirror is only a restore
source for when the store has no live entry.

**Template:** the unlocked sibling CND2048Y34 (T95, same 4544 B UserCred
format) differs from the locked KD blob in only **21 bytes**: the AdminPW
UTF-16 name at +0x10, the record counter at +0x8 (`01…` → `ff ff ff ff`), the
record flag at +0x3C, and record-presence flags at +0x1010/+0x1018/+0x1020
(all `01/00` → `ff`). Tails (including any signature area) are byte-identical.

**Patch:** `unlock_s92_v3.py` replaces the UserCred CONTENT with the unlocked
unit's 4544 B blob, keeping state LIVE (0x3F), in every store copy.

`BINs/W25Q256FV_SOIC8-CND14004KD-UNLOCKED-V3.BIN` md5
`e710f6589cdf85802fbb35acf1bafbe2` — verified: differs from the original dump in
exactly the 21 semantic bytes (0x18D4AAE–0x18D5AC9).

**Bench protocol:** flash V3 → boot → try Setup. Expected: no password prompt
(store-side validation sees no AdminPW) and NO re-injection (live entry
exists). Re-read the chip after one boot to confirm the blob stayed.

## 9. V3 RESULT — RE-INJECTED ANYWAY (2026-11-17)

Flashed V3; password remained. Afterflash dump
(`W25Q256FV_SOIC8-CND14004KD-AFTERv3FLASH.BIN`, md5
`28607c8367d8d95722834f0c93c4e5f0`):

- our empty-live entry @0x18D4A58 was **demoted to 0x3C** (deleting),
- a second 0x3C staging entry appeared @0x18DF160,
- a **new live UserCred @0x18E0370 with the LOCKED content** — the EC mirror
  replaced the empty blob outright.

**Verdict: on S92 the EC mirror is fully authoritative** — it re-syncs
whenever the store differs from the EC, even when a live entry exists. Unlike
the 830 G5 (where mirror-era code tolerated an empty skeleton), S92 treats the
store as a pure cache. **Store-level patching is exhausted; the EC must be
cleared (or the sync code patched).**

## 10. EC identified: Nuvoton, 1 MB external SPI

The repair RAR's third file (`zbook 1m.bin`, 1,049,344 B) is the **EC firmware
flash**: Nuvoton NPCX layout (`APP EM`, `DROM`, `ARC PARM`, `EE_*` event
strings, "HP ZBook 15/17 G7 Mobile Workstation"). So LA-J202P's EC is a
Nuvoton part with a 1 MB external SPI holding APP+DROM.

The EC route is therefore concrete: **dump KD's own 1 MB EC SPI chip**, then
either (a) locate the credential mirror / passphrase structure and crack the
Siemens 8-char password (hashcat -m 130), or (b) clear the credential region
and write back. The donor's EC dump has no credential (unlocked unit) and is a
useful layout reference only.

## 12. YES — EC vars CAN be set through the 32 MB chip (S92 map, 2026-11-17)

The question: can flashing only the 32 MB main IC change the EC's credential
state? Answer: **yes** — the SMM code that lives in the 32 MB chip owns the EC
named-value write; Setup's "clear password" uses exactly this path. Full map
in `CredentialServicesSmm` (S92 01.08, module 121):

| VA | role |
|---|---|
| 0x14A0 | **SMC named-value WRITE helper** (EC write) |
| 0x2960 | SMC named-value read helper |
| 0x5640–0x5730 | credential **sync/SET handler** (SMC read → EC write; == 830 G5's 0x52cc) |
| **0x5716** | `mov [rsp+0x20],2` + `call 0x14A0` — **EC credential WRITE, opcode 2** (== 830 G5's 0x2214); args: rcx=descriptor, r8=[record+0x16] data, r9=[record+0xe] size-field, edx=8 |
| 0x5960 / 0x5A10 | GetVariable / SetVariable wrappers (r9d=0xB attrs) |
| 0x68D4–0x6Cxx | UserCred blob builder (builds store blob from records) |
| 0x6D48 | SMC read with descriptor (used by restore) |
| data 0x74C0 | SmcInProgress-style gate flag (checked at 0x6764) |
| data 0x74E0/0x7500/0x7510/0x7530 | name table: UserCred / AdminPW / BeamLocalUser1 / BeamRemoteUser |

Write-call sites with opcode 2: 0x5716 (EC credential write), 0x59C6/0x5A9E
(var protocol writes). The **clear** = the 0x5716 write with an EMPTY record
(zeroed data) — the same call Setup makes when the user clears the password.

### Patch design (main-flash-only EC clear)

1. Trace the boot-time restore trigger (SMM comm opcode from the
   SmcInProgress-cluster module — S92 analog of T95's 525/86/94) — the last
   unknown. The restore reads EC via 0x2960/0x6D48 and writes the store via
   the 0x59C6/0x5A9E wrappers.
2. Patch candidate **A (preferred): re-route the boot restore to perform the
   EC WRITE with an empty record** — e.g. in the sync handler (0x5640) force
   the write branch with a zeroed record struct, or patch the restore caller
   to invoke the clear opcode instead. One boot then clears the EC mirror
   legitimately (same transaction Setup uses) and the store stays empty.
3. Patch candidate **B**: NOP the restore's store-write (`call` at the
   wrapper) AND patch the gate flag 0x74C0 — only if validation turns out
   store-side (not proven on S92; V3 evidence suggests EC-authoritative).
4. Mechanics unchanged: patch the PE in-place (same length), swap via
   `UEFIReplace` (win64 on the bench) into FFS 121 of
   `CND14004KD_BIOS_region.rgn`, splice back at 0x1000000–0x1FFE000 keeping
   the unit boot block, flash, re-read.

Priority note: the EC-SPI route (section 10) still has the highest
certainty — the code patch is the no-soldering alternative.
